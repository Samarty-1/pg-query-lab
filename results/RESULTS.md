# Results

Generated by `python -m lab.bench`. Do not edit by hand.

PostgreSQL 17.6, database 2234 MB, shared_buffers 2GB, work_mem 4MB, random_page_cost 4, max_parallel_workers_per_gather 2, jit on.

Rows: users 1,477,024, posts 945,111, comments 1,532,817, votes 4,935,185, badges 2,004,443, tags 3,162, post_links 221,126, post_tags 1,162,642.

Time is the median of 7 runs after 2 warm-up runs, measured on the client with every row fetched. Buffers are 8 kB pages touched (cache hits + reads) in one run. "Same rows" compares a hash of the result with the first variant's.

## 01_user_timeline: The 20 most recent posts by one user

The profile page: the latest 20 posts by one user, newest first. The user picked is the
most prolific author on the site (4,428 posts), which is the worst case for this page.

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| no index | 155 | - | 96,926 | 20 | - | - | Seq Scan on posts (2 workers) |
| index on (owner_user_id) | 1.97 | 79x faster | 4,016 | 20 | yes | 11.9 MB | Index Scan using exp_posts_owner |
| index on (owner_user_id, creation_date DESC, id DESC) | 0.16 | 965x faster | 22 | 20 | yes | 36.6 MB | Index Scan using exp_posts_owner_recent |

- *index on (owner_user_id)*: Finds the rows for the user through the index, but still fetches and sorts all of them to keep 20.
- *index on (owner_user_id, creation_date DESC, id DESC)*: The index is already in the order the page wants, so the scan stops after 20 entries and nothing is sorted.

## 02_tag_search: The 50 newest questions with a given tag

Tags arrive in the dump as one string per question, `|bash|scripts|`. The loader also
splits them into a `post_tags (post_id, tag_id)` table. Which shape answers "newest 50
questions tagged bash" fastest, and does the junction table's primary key help?

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| LIKE on the tag string | 174 | - | 96,926 | 50 | - | - | Seq Scan on posts (2 workers) |
| junction table, primary key (post_id, tag_id) only | 127 | 1.4x faster | 50,126 | 50 | yes | - | Seq Scan on post_tags; Index Scan using tags_name_unique; Index Scan using posts_pkey (2 workers) |
| junction table + index on (tag_id, post_id) | 22.3 | 7.8x faster | 44,882 | 50 | yes | 24.9 MB | Index Scan using tags_name_unique; Index Only Scan using exp_post_tags_tag; Index Scan using posts_pkey |
| trigram index on the tag string | 12.2 | 14x faster | 10,663 | 50 | yes | 32.3 MB | Bitmap Heap Scan on posts; Bitmap Index Scan using exp_posts_tags_trgm |
| junction table carrying creation_date, index on (tag_id, creation_date DESC, post_id DESC) | 0.41 | 423x faster | 256 | 50 | yes | 103.0 MB | Index Scan using tags_name_unique; Index Only Scan using exp_post_tags_recent; Index Scan using posts_pkey (50 heap fetches) |

- *junction table, primary key (post_id, tag_id) only*: The key starts with post_id, so it cannot be used to look up a tag: the whole junction table is read.
- *trigram index on the tag string*: Keeps the original LIKE query unchanged; costs a much larger index.
- *junction table carrying creation_date, index on (tag_id, creation_date DESC, post_id DESC)*: Every earlier variant must fetch all 11,211 bash questions to find the newest 50. Copying the (immutable) creation date into the junction row lets the index hand back the newest 50 directly.

## 04_date_range: Up-votes per day over the last month

A dashboard query over the biggest table (4.9M votes): up-votes per day since
1 March 2024. Five ways to index a date range, with what each index costs on disk.

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| no index | 151 | - | 31,650 | 31 | - | - | Seq Scan on votes (2 workers) |
| BRIN on (creation_date) | 513 | 3.4x slower | 31,538 | 31 | yes | 48 kB | Bitmap Heap Scan on votes; Bitmap Index Scan using exp_votes_date_brin |
| BRIN on (creation_date), on a copy of the table stored in date order | 3.58 | 42x faster | 194 | 31 | yes | 48 kB | Bitmap Heap Scan on exp_votes_sorted; Bitmap Index Scan using exp_votes_sorted_brin |
| B-tree on (creation_date) | 12.6 | 12x faster | 7,559 | 31 | yes | 34.1 MB | Bitmap Heap Scan on votes; Bitmap Index Scan using exp_votes_date |
| B-tree on (creation_date, vote_type_id) | 1.99 | 76x faster | 18 | 31 | yes | 35.1 MB | Index Only Scan using exp_votes_date_type |
| partial B-tree on (creation_date) WHERE vote_type_id = 2 | 3.25 | 46x faster | 14 | 31 | yes | 24.9 MB | Index Only Scan using exp_votes_up_date |

- *BRIN on (creation_date)*: A BRIN index stores one min/max per range of pages. Votes.xml is not in id or date order (physical correlation 0.61), so recent votes sit in 24% of the pages, spread across every range: the index rules nothing out, and the scan it produces is not parallel.
- *BRIN on (creation_date), on a copy of the table stored in date order*: Same rows, same kind of index, 48 kB. The only change is the physical order of the rows.
- *B-tree on (creation_date, vote_type_id)*: Both columns the query needs are in the index, so the table itself is never read (index-only scan).

## 06_not_in_null_trap: Users who have never posted

Three ways to write an anti-join. 16,835 posts have no owner (the account was deleted),
so the sub-select contains NULLs. `x NOT IN (..., NULL)` is never true, so the obvious
NOT IN query returns zero users instead of 1.16 million, and at the default work_mem
it does not even finish.

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| NOT EXISTS | 489 | - | 127,591 | 1 | - | - | Seq Scan on posts; Seq Scan on users (spilled 13,778 temp blocks, 2 workers) |
| LEFT JOIN ... IS NULL | 694 | 1.4x slower | 127,621 | 1 | yes | - | Seq Scan on posts; Seq Scan on users (spilled 14,691 temp blocks, 2 workers) |
| NOT IN, default work_mem (4MB) | > 20,000 (cancelled) | did not finish | - | - | - | - | Seq Scan on users; Seq Scan on posts |
| NOT IN, work_mem 256MB | 655 | 1.3x slower | 321,147 | 1 | **no** | - | Seq Scan on users; Seq Scan on posts (2 workers) |
| NOT IN with NULLs filtered, work_mem 256MB | 712 | 1.5x slower | 321,147 | 1 | yes | - | Seq Scan on users; Seq Scan on posts (2 workers) |

- *NOT IN, default work_mem (4MB)*: The id list does not fit in work_mem, so Postgres re-scans it for every user: about 1.5M x 0.9M comparisons. Cancelled at the time limit.
- *NOT IN, work_mem 256MB*: Now it finishes, with the wrong answer: 0. One NULL in the list makes NOT IN unknown for every row.

## 08_title_search: Search question titles

"nvidia ... driver" somewhere in a title. A leading wildcard defeats a B-tree index;
a trigram index serves the same ILIKE query unchanged; full-text search is a different,
word-based question and returns a different set of rows.

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| ILIKE, no index | 237 | - | 96,912 | 2,678 | - | - | Seq Scan on posts (2 workers) |
| ILIKE + B-tree on (title) | 225 | 1.1x faster | 96,912 | 2,678 | yes | 34.4 MB | Seq Scan on posts (2 workers) |
| ILIKE + trigram GIN on (title) | 6.62 | 36x faster | 2,889 | 2,678 | yes | 60.7 MB | Bitmap Heap Scan on posts; Bitmap Index Scan using exp_posts_title_trgm |
| full-text search + GIN on to_tsvector(title) | 3.89 | 61x faster | 2,763 | 2,784 | no, by design | 16.6 MB | Bitmap Heap Scan on posts; Bitmap Index Scan using exp_posts_title_fts |

- *ILIKE + B-tree on (title)*: Not used: a pattern that starts with % has no prefix to search the B-tree with.
- *full-text search + GIN on to_tsvector(title)*: Matches the words in any order and any form (driver, drivers), and treats nvidia-driver-535 as separate words, so the row set differs on purpose.

## 09_unindexed_foreign_keys: Delete five posts

Postgres indexes the referenced side of a foreign key (it must be a primary key or
unique) but not the referencing side. Deleting a post makes it check every table that
points at posts: comments, votes, post_links (twice) and posts itself (parent_id,
accepted_answer_id). Without an index on those columns each check is a full scan, once
per deleted row. The five posts chosen have nothing pointing at them, so the delete is
legal; it runs inside a transaction that is rolled back.

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| referencing columns not indexed | 4,607 | - | 36 | 5 | - | - | Seq Scan on exp_victims; Index Scan using posts_pkey |
| referencing columns indexed | 3.75 | 1,229x faster | 36 | 5 | yes | 20.8 MB + 54.3 MB + 4.1 MB + 2.6 MB + 9.4 MB + 2.9 MB | Seq Scan on exp_victims; Index Scan using posts_pkey |

- *referencing columns not indexed*: The plan for the DELETE itself is trivial; the time is in the foreign-key triggers, which the buffer count does not include.

## 10_extended_statistics: Posts per holder of one gold badge

The planner multiplies the selectivity of each filter as if columns were independent.
A badge name fixes its class ("Famous Question" is always gold), so
`name = 'Famous Question' AND class = 1` is estimated as 2% x 2.4% of badges when the
truth is 2%. Extended statistics on (name, class) tell the planner about the

## 11_index_not_worth_using: The date of the latest vote of one type

An index is not always the faster path. Vote type 2 (up-vote) is 73% of the table;
type 7 (reopen) is 198 rows. The same index on (vote_type_id) is offered for both.
For the common value the planner ignores it; forcing it shows the planner was right.
The last two variants ask about the rare value, so they return a different row and
their times should be compared with each other, not with the first variant.

| Variant | Median ms | vs first | Buffers | Rows | Same rows | Extra storage | Plan |
|---|---:|---:|---:|---:|---|---:|---|
| common value, no index | 190 | - | 31,536 | 1 | - | - | Seq Scan on votes (2 workers) |
| common value, index on (vote_type_id) available | 196 | same | 31,536 | 1 | yes | 32.6 MB | Seq Scan on votes (2 workers) |
| common value, index forced (enable_seqscan = off) | 230 | 1.2x slower | 34,526 | 1 | yes | - | Bitmap Heap Scan on votes; Bitmap Index Scan using exp_votes_type (2 workers) |
| rare value, no index | 140 | 1.4x faster | 31,536 | 1 | no, by design | - | Seq Scan on votes (2 workers) |
| rare value, same index | 0.17 | 1,107x faster | 96 | 1 | no, by design | - | Index Scan using exp_votes_type |

- *common value, index on (vote_type_id) available*: The index exists and the planner still reads the whole table.
